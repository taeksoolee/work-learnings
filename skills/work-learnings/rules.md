# work-learnings — 배움 기록 규칙

작업 중에 **사용자가 배울 수 있는 것**을 저장소 안 `docs/learnings/` 에 카테고리별로 쌓는다.
할 일을 뽑는 도구가 아니라 **배움을 위한 도구**다. 기록은 언제나 **제안 → 승인** — 사용자가 고른 것만 쓴다.

기계적 동작(항목 추가·색인 갱신·검사)은 손으로 하지 말고 스크립트를 쓴다 — 사람·세션이 달라도 결과가 같아야
하기 때문이다. 스크립트는 이 파일 옆 `scripts/learnings.mjs` 이고, **저장소 루트에서** 설치 경로로 실행한다
(Claude Code 설치 기준 `.claude/skills/work-learnings/scripts/learnings.mjs`).

```sh
W=.claude/skills/work-learnings/scripts/learnings.mjs   # 설치 위치에 맞게
node $W add --category ui-ux --title "모바일 칩 가로 스크롤은 오른쪽 여백 없이 화면 끝까지 넘긴다" \
  --why "끝이 잘려 보여야 가로로 더 있다는 신호가 된다." --when "모바일에서 가로로 스크롤되는 칩·카드·탭 목록" \
  --source "a1b2c3d 모바일 필터 칩" --date 2026-09-26
node $W add --stdin <<'EOF'      # 값에 백틱·$ 가 있으면 JSON 으로 (셸 이스케이프 없이)
[{"category": "data", "title": "…", "why": "`${table.col}` 은 …", "when": "…", "source": "…", "date": "2026-09-26"}]
EOF
node $W list
node $W lint
```

## 무엇을 남기나

판단 기준 한 줄: **"다른 프로젝트에서 같은 상황을 만나면 이 한 줄이 도움이 되는가?"**

- **남긴다** — 이 프로젝트 밖에서도 통하는, 사용자가 다음에 써먹을 수 있는 교훈.
  - UI/UX 원칙 ("칩 가로 스크롤은 엣지까지"), 함정과 그 이유 ("IME 조합 중 Enter 는 keydown 에서 isComposing 확인")
  - 도구·언어의 비직관적 동작, 디버깅에서 통한 접근, AI 와 협업하며 알게 된 것
- **남기지 않는다** — 다른 곳이 정본인 것.
  - 이 프로젝트만의 결정 → 프로젝트 문서(DECISIONS 등)
  - 할 일·버그 → 일감 (repo-tickets 를 쓰면 `docs/tickets/`)
  - 코드에서 바로 보이는 것, 일회성 사실, 이미 널리 알려진 상식

**억지로 만들지 않는다.** 노이즈가 이 도구의 가장 큰 위험이다 — 애매하면 제안하지 않는다.

- **개수는 기준이 정한다.** 후보마다 묻는다: **"다른 프로젝트에서 이걸 몰랐다면 실제로 시간을 잃었을까?"**
  통과한 것은 전부 낸다(많아야 3개), 통과하지 못하면 0개다. 0개·1개·2개·3개 모두 정상이다.
- **어느 숫자로도 맞추지 않는다** — 3개를 채우려고 약한 후보를 붙이지 않고, "적게 내는 게 안전하다" 며
  통과한 후보를 1개로 줄이지도 않는다. 3개를 넘게 통과했으면 시간을 가장 많이 아껴 줄 3개를 낸다.
- **대상은 "이번 작업에서 사용자가 접한 것"** 이다 — 이 세션이 처음 알아낸 것만이 아니다. 다른 사람·세션의 분석을
  이번 작업에서 다시 확인했어도, 사용자가 이번에 처음 접했다면 후보다. 이미 기록된 것(`list`)은 제외.

## 제안 → 승인

1. **언제 제안하나**: 작업을 마치고 **최종 보고**할 때, 그 작업에서 일반화 가능한 교훈이 있었을 때만.
   최종 보고는 사용자에게 작업 결과를 알리는 마무리 응답이다 — 다른 세션이 맡긴 일을 처리한 결과도 포함.
   작업 중간의 확인 질문·선택지 제시·진행 보고에는 붙이지 않는다.
   (이 규칙은 CLAUDE.md·AGENTS.md 의 진입 블록이 매번 상기시킨다 — skill 은 저절로 켜지지 않는다.)
2. **형식** — 보고 끝에 이 모양 그대로. 많아야 3개(상한). 없으면 섹션 자체를 쓰지 않는다.
   ```
   배울 거리
   1. [ui-ux] 모바일 칩 가로 스크롤은 오른쪽 여백 없이 화면 끝까지 — 잘린 끝이 "더 있다" 신호
   2. [testing] …
   ```
   `[카테고리] 제목 — 왜 한 줄`. 제목은 아래 "쓰는 방식" 을 따른다. 예시의 줄 수는 형식일 뿐 개수가 아니다.
3. **승인**: 사용자가 "1 기록", "전부" 처럼 고른 것만 `add` 로 쓴다. 제안 줄의 `제목 — 왜` 는
   앞쪽만 `--title`, 뒤쪽은 `--why` 로 옮긴다 (제목에 ` — ` 를 남기면 `add` 가 거부한다). 고르지 않은 것은 다시 꺼내지 않는다.
   **승인 없이 기록하지 않는다** — "기록해 둘게요" 도 금지. 제안은 제안으로 끝낸다.
   여러 개를 고르면 `add --stdin` 에 JSON 배열로 한 번에 넣는다.
4. 기록하고 나면 무엇을 어디에 썼는지(`파일:줄`) 한 줄로 알린다.

### 저장소에서 찾기

사용자가 "이 저장소에서 배울 거리 찾아줘" 처럼 직접 요청하면, 작업 보고가 아니어도 같은 형식으로 제안한다.

- `node $W hints` 로 **단서**를 본다:
  - 고친·되돌린·다시 짠 커밋과 `ci`·`build` 커밋 — 본문 긴 것 먼저(같으면 이유 표현이 많은 것).
    머지 커밋, Revert 자동 본문, 스쿼시 본문의 하위 커밋 제목 나열, 트레일러는 본문으로 치지 않는다.
    본문 없는 Revert 는 목록에 넣지 않고 개수만 센다.
  - `HACK`·`주의`·`우회`·`함정`·`조용히`·`깨진다` 같은 주석 — 같은 문장은 한 번, 파일당 3개, 폴더를 번갈아.
  - 주의 문서 — `CAVEATS.md`·`TROUBLESHOOTING.md` 같은 파일(제목 목록과 함께), md 의 주의·함정 제목.
  - repo-tickets 를 함께 쓰면 완료 일감 — `원인`·`재현`·`배운 것` 같은 절이 있는 것 먼저.
- **단서는 배울 거리가 아니다** — 해당 커밋(`git show`)·코드·문서·일감을 읽고 판단한다. 단서가 가리키는 문서
  ("함정은 X/README.md 에 정리돼 있다")도 따라가 읽는다. 단서가 많아도 결과는 0개일 수 있다.
  - 본문 없는 커밋은 제목만으로 판단하기 어려워 따로, 5개까지만 보인다 (`--all`). 오래된 저장소는 `--since "6 months ago"`.
  - `(CI·빌드)`·`(설정)`·`(문서)` 는 바뀐 파일이 그것뿐인 커밋이다. `(설정)`·`(문서)` 는 프로젝트 설정·문서 정리일 때가
    많으니 특히 기준으로 거른다. `(CI·빌드)` 는 CI·빌드 도구의 함정이 배울 거리인 경우가 많다 — 표시는 "덜 중요" 가 아니다.
  - 순서는 추정이다 — 위쪽이 변경 규모가 큰 리팩터 시리즈나 프로젝트 사정일 수 있고, 좋은 후보가 아래에 있을 수 있다.
    위에서 몇 개만 보고 멈추지 않는다.
  - 단서가 못 보는 곳: 이번 세션에서 겪은 일 — 커밋에 교훈으로 남지 않는다. 이건 작업 보고 끝 제안이 맡는다.
- 판단 기준은 위와 같다. 코드를 훑으면 **이 프로젝트만의 결정**과 **코드에 이미 보이는 것**이 가장 많이 걸린다 —
  둘 다 남기지 않는다. 고친 이유가 "이 프로젝트의 사정" 이 아니라 "그 도구·플랫폼이 원래 그렇다" 일 때가 배울 거리다.
- **특정 버전 도구의 함정**은, 사용자가 그 도구를 다시 쓸 만하면 남긴다 — `언제` 에 도구와 버전 범위를 적는다
  ("PocketBase 0.22 이하에서 schema 를 통째로 갱신할 때"). 이미 고쳐진 버전만 쓰게 될 거라면 남기지 않는다.
- 이미 기록된 것(`list`)과 겹치면 제안하지 않거나, 보강할 점이 있으면 "갱신" 으로 제안한다.
- 개수 기준은 같다 — 통과한 것만, 많아야 3개, 0개도 정상. 요청이 "더" 면 남은 후보 중 **기준을 통과한 것만**.
  없으면 "찾아봤지만 기준을 통과한 게 없다" 고 보고한다. 출처는 커밋 해시나 `파일:줄`.

## 쓰는 방식

카테고리 하나 = 파일 하나 (`docs/learnings/<카테고리>.md`). 항목 하나:

```markdown
## 모바일 칩 가로 스크롤은 오른쪽 여백 없이 화면 끝까지 넘긴다

- 왜: 끝이 잘려 보여야 가로로 더 있다는 신호가 된다. 오른쪽 여백이 있으면 목록이 끝난 것처럼 보인다.
- 언제: 모바일에서 가로로 스크롤되는 칩·카드·탭 목록.
- 출처: 2026-09-26, a1b2c3d 모바일 필터 칩
```

- **제목(`##`)이 곧 배운 것이다** — 한 줄 규칙(명령형/서술형 현재형). 질문형·감상("~가 어려웠다") 금지.
  제목만 훑어도 쓸모 있어야 한다. 배운 것 **하나**만 — 이유는 `왜`, 조건은 `언제` 로 (` — ` 로 이어 붙이지 않는다).
  60자 안팎이면 충분하다. 코드·API 이름은 백틱(`` `overflow: auto` ``), 말을 인용할 때는 「」를 써도 된다.
- `왜`·`언제`·`출처` 는 필수. `출처` 는 `YYYY-MM-DD, ` 로 시작하고 일감 참조(repo-tickets 의 `[[이름]]`)·커밋 해시·작업 한 줄을 붙인다.
  날짜는 **그 일이 있던 날**(커밋·작업 날짜, `add --date`)이다. 출처가 커밋 해시로 시작하면 `add` 가 그 커밋 날짜를
  쓴다. 그 밖에는 `--date` 가 없으면 기록한 날.
- 예시 코드는 필드 아래에 짧게 (선택). 길어지면 교훈이 아니라 문서다.
- **이 프로젝트의 이름·경로로 설명하지 않는다** — 다른 프로젝트에서 읽혀야 한다. 프로젝트 고유의 것은 `출처` 에만.
- **같은 교훈은 새로 쓰지 않고 기존 항목을 갱신한다** — `왜`·`언제` 를 보강하고 `- 출처:` 줄을 하나 더 단다.
  `add` 는 비슷한 제목이 있으면 멈춘다. 정말 다른 교훈일 때만 `--force`.
  기존 항목은 손으로 고치고, 끝나면 `lint`.

## 카테고리

처음엔 고정 목록. 파일명 = 카테고리 id. 항목이 어디에 맞는지 애매하면 **"사용자가 나중에 어디서 찾을까"** 로 고른다.

| id | 범위 |
|---|---|
| `ui-ux` | 화면 배치·인터랙션·접근성·모바일 UX |
| `frontend` | 프레임워크·상태·렌더링·브라우저 동작 |
| `backend-api` | API 설계·인증·에러 계약·서버 런타임 |
| `data` | DB·스키마·마이그레이션·쿼리 |
| `testing` | 테스트 전략·재현·회귀 |
| `devops-ci` | 빌드·배포·CI·인프라·개발 도구 (셸·스크립트·로컬 도구 설정 포함) |
| `git` | 브랜치·커밋·히스토리 다루기 |
| `ai-collab` | AI·에이전트와 일하는 방법 |
| `architecture` | 구조·경계·의존성 |
| `performance` | 측정·최적화 |
| `security` | 보안 |

- **새 카테고리는 기존 어디에도 안 맞는 항목이 3개 이상 쌓였을 때만**, 사용자에게 확인받고
  `category <id> --scope "<범위>" --reason "<근거>"` 로 추가한다. 근거는 색인(`README.md`)의 "추가 카테고리" 에 남는다.
  카테고리를 늘리는 것보다 기존 카테고리에 넣는 쪽이 낫다 — 저장소끼리 카테고리가 같아야 나중에 모아 볼 수 있다.

## 스크립트

`node .claude/skills/work-learnings/scripts/learnings.mjs <명령>` — 저장소 루트에서 실행.

| 명령 | 하는 일 |
|---|---|
| `init` | `docs/learnings/` + 색인(`README.md`) 생성 |
| `add --category C --title T --why W --when N --source S [--date D] [--force]` | 항목 추가 + 색인 갱신. 비슷한 제목이 있으면 멈춘다(`--force` 로 강행), 같은 제목은 강행도 안 된다. 날짜는 `--date` 로만 (`--source` 에 넣으면 거부) |
| `add --stdin [--force]` | 같은 일을 JSON 입력으로 — 객체 하나 또는 배열(여러 항목을 한 번에, 하나라도 걸리면 아무것도 안 쓴다). 값에 백틱·`$` 가 있을 때 |
| `list [카테고리]` | 카테고리별 제목 목록 |
| `lint [--fix]` | 형식 검사. 오류가 있으면 종료 코드 1. `--fix` 는 색인만 다시 만든다 |
| `category <id> --scope S --reason R` | 카테고리 추가 (근거를 색인에 기록) |
| `hints [--limit N] [--since D] [--all]` | 배울 거리가 숨어 있기 쉬운 커밋·주석·주의 문서·완료 일감 단서 (git 저장소에서만, 절마다 기본 30개, 본문 없는 커밋은 10개) |

- **색인(`docs/learnings/README.md`)은 스크립트가 만든다 — 손으로 고치지 않는다.** 항목을 손으로 고쳤으면 `lint --fix`.
- `lint` 가 보는 것:
  - 오류: 모르는 카테고리 파일, 필수 필드(`왜`·`언제`·`출처`) 누락, 날짜로 시작하지 않는 `출처`,
    같은 제목(대소문자·문장부호 무시), 색인 불일치.
  - 경고: 비슷한 제목, 질문형 제목, ` — ` 가 든 제목, 날짜가 둘인 출처, 하위 폴더.
- **비슷한 제목 판정은 추정이다** — 조사·어미를 떼고 낱말이 얼마나 겹치는지만 본다. 다른 교훈인데 경고가 나면
  제목을 더 구체적으로 고친다 (구분이 안 되는 제목은 읽는 사람도 헷갈린다).
- 버전은 이 파일 첫 줄이 정본이고 `lint` 출력에 나온다.
